**am 개선 요청** — 사용자 지시로 넘깁니다. 저는 어제부터 issue-repo 에서 **6개 에이전트에 작업을 분배하고 진행을 추적하는 매니저 역할**을 하고 있고, 하루 동안 am 을 실사용하며 막힌 지점을 정리했습니다. 전부 **실제로 겪은 것**이고 가정은 없습니다.

결론부터: **가장 큰 문제는 기능 부재가 아니라 (1) 메시지 이력이 am 에 안 쌓임 (2) 이미 있는 명령을 아무도 안 씀 — 둘입니다.**

# A. 이미 있는데 아무도 안 써서 사고가 난 것

am 에 이미 `claim` / `register` / `review` / `decide` 가 있는데 저를 포함해 **아무도 안 썼습니다.** 어제 실제 사고 둘:

**① PR 중복** — main 이 시맨틱 충돌로 적색이 됐을 때, 두 세션이 서로 모른 채 같은 파일의 같은 수정을 각각 PR 로 올렸습니다(server#N / #N, 5분 차). 한쪽이 저에게 "이미 착수한 사람 있나" 물었는데 제가 **제 착수 여부만** 확인하고 "없다"고 답했습니다.

**② 이슈 중복** — 같은 결함(포맷 비대칭)을 두 세션이 82분 차로 이슈 발행(#N / #N). 제가 낸 쪽을 닫았습니다.

둘 다 `am claim --paths ... --branch ... --issue ...` 가 있었으면 구조적으로 막혔습니다. 그리고 `am ask --owner-of <워크트리 경로>` 를 실제로 시도했는데 **no-owner** 로 실패했습니다 — `register` 가 안 돼 있어서입니다.

**요청 A — 기능 추가보다 채택 강제가 먼저입니다:**
- 세션 시작 훅에서 `am register` 자동 실행(세션 id·cwd·task 는 이미 알 수 있음)
- `--owner-of` 가 no-owner 일 때 "등록된 소유자 없음. 대신 이 경로를 최근 만진 세션: …" 로 폴백(git log·워크트리 스캔). 지금은 그냥 실패라 쓸모가 없습니다
- `claim` 충돌 시 경고를 **양쪽에** 발송

# B. 정말 없어서 막힌 것 (우선순위 순)

## B-1 (최우선) 메시지에 타임스탬프가 없다

제가 받는 cross-session 메시지에 **발신 시각이 없습니다.** 그래서 "각 에이전트가 몇 분 전에 마지막으로 응답했나"라는 질문에 답할 방법이 없었고, GitHub 커밋·PR·코멘트 시각으로 **근사**해야 했습니다.

그 결과 사용자에게 **틀린 답**을 했습니다 — "몇 분 사이라 담당들이 아직 작업 중"이라고 했는데 실제로는 **3~6시간 정지**였습니다. 매니저 역할의 기본(누가 언제 무엇을 말했나)이 불가능합니다.

요청: 수신 메시지에 발신 시각(ISO8601) 포함.

## B-2 (최우선) 이력이 am 안에 안 쌓인다 — 두 채널이 갈려 있다

- `am ask` 로 보낸 것은 상대에게 도착합니다(ok:true, thread id 반환)
- 그런데 상대의 답은 **harness 의 cross-session 경로**로 오고, `am inbox` 는 하루 종일 빈 배열이었습니다
- 반환받은 thread id(t-e714dd17 등)로 `am read` 를 해도 **빈 결과**입니다

즉 thread 라는 개념은 있는데 **조회가 안 됩니다.** 대화가 am 밖에서만 존재해서 세션이 바뀌면 이력이 통째로 사라집니다.

요청: 송신·수신을 같은 스토어에 적재하고 `am read <thread>` 가 실제 메시지를 반환.

## B-3 마지막 활동 시각

`am agents` 는 live-active / live-idle 은 주지만 **언제부터 idle 인지**를 안 줍니다. **5분 idle 과 6시간 idle 은 관리 판단이 완전히 다릅니다**(전자는 대기, 후자는 개입 신호).

요청: last_activity 또는 idle_for 필드.

## B-4 브로드캐스트

중복 방지 공지를 6명에게 보내려면 6번 호출합니다. 어제 같은 메시지를 3~6명에게 보낸 게 네 번 있었습니다.

요청: --to 다중 지정 또는 --all / --state live-idle 필터 발송.

## B-5 정체성이 세 축으로 갈려 있다

같은 에이전트를 세 이름으로 부릅니다:
  ListAgents : issue-repo-ai-19
  소켓       : uds:/tmp/cc-socks/9213.sock
  am         : session-ecb70ba5

어제 실제 혼선 — 한 세션이 "제 ListAgents 에 issue-repo-ai-19 가 없습니다"라며 배정 충돌을 의심했습니다. **자기 자신은 목록에 안 나오기 때문**이었고, 제가 "당신이 그 이름입니다"라고 추론해서 풀었습니다. 도구가 해결할 문제입니다.

요청: `am agents` 가 세 축을 한 행에 표시. 자기 자신도 (you) 표시로 포함.

## B-6 작업 보드

지금 "누가 무엇을 어느 단계까지"를 **제 대화 기억으로** 유지합니다. `claim` 이 이미 있으니 그걸 **읽는 뷰**만 있으면 됩니다.

요청: `am board` — claim 된 이슈·경로·브랜치를 소유자·상태와 함께 표로.

# 참고: 잘 작동한 것

비판만 있으면 균형이 안 맞으니 — `am ask --to <session>` 자체는 하루 종일 **안정적**이었습니다. 전송 실패 0건이고 긴 마크다운 본문(수천 자·표·코드블록)이 손실 없이 전달됐습니다.

그리고 `am agents` 가 세션의 **원래 주제**를 보여주는 것이 결정적으로 유용했습니다 — 어제 "#N(분석 단계)을 누구에게 줄까"를 정할 때 ListAgents 의 issue-repo-ai-* 이름으로는 불가능했고, "분석 단계가 왜 이렇게 오래걸리는지 분석해줘"라는 원 주제를 보고 배정했습니다. **그 판정 축은 유지해 주세요.**

# 우선순위

B-1 · B-2 가 압도적입니다. 나머지는 있으면 좋은 정도이고, A 는 기능이 아니라 규약 문제라 훅·폴백으로 푸는 게 맞다고 봅니다.

질문 있으시면 물어 주세요. 실사용 맥락이 필요하면 구체 사례를 더 드릴 수 있습니다.

# 08-22 추가 — 배달 신뢰성 결함 4종 (실측)

앞선 피드백 이후 다시 PM 역할로 4개 이슈를 3개 세션에 분배·중개했다. 이번엔 기능 부재가 아니라 **배달 자체가 불안정**해서, 결국 **모든 지시를 GitHub 이슈 코멘트로 옮기고 am 은 "왔는지 확인용"으로만 썼다.** 근거는 전부 `am read` 원본 필드다(메신저 스레드 t-851876d6 로도 보고함).

> 참고: 예전 B-1("메시지에 타임스탬프가 없다")은 해결된 것으로 보인다 — `am read` 에 `created`·`injected_at` 이 있어 이번 분석이 가능했다. 고맙다. 다만 그 값들이 `inbox` 요약에는 안 보인다.

## A (최우선) — "미배달 만료" 통지가 거짓이다

```
m-5cd30c40  17:20:31 → session-39c60741
  state=expired · inject=1 · injected_at=17:20:35   ← 발송 4초 만에 주입됨
릴레이 통지: "미배달 만료 … TTL 초과. 수신자가 유휴/종료 상태였을 수 있다."
```
**배달됐는데 미배달로 보고**하고, 원인까지 사실과 다르게 단정한다. 나는 그 통지를 믿고 같은 내용을 재발송한 뒤 채널 자체를 이슈로 옮겼다 — **오진이 운영 판단을 바꿨다.**

가설: 만료 판정이 "배달 여부"가 아니라 "종결(answered) 도달 여부"로 계산되고, 통지 문구가 그걸 미배달로 서술한다. `consult`/`normal` 처럼 답이 선택인 타입은 injected 로 끝나는 게 정상인데 실패로 집계된다.

- state 를 `delivered_unanswered` / `undelivered` 로 분리
- `inject_count > 0` 이면 문구에서 "미배달"·"유휴/종료" 단정 제거 → "무응답 만료"
- 답이 선택인 타입은 만료 통지를 내지 않거나 fyi 로 강등

## B — live-active 세션인데 TTL 1시간 내내 주입 0

```
m-700a420f 17:35:23 → session-39c60741  inject=0
m-fe39691e 17:36:01 → session-39c60741  inject=0
m-a66ca128 17:36:02 → session-85a4d512  inject=0
```
같은 시각 `am agents` 는 두 수신자를 모두 `live-active idle:0m` 으로 보고했다. 같은 수신자에게 앞뒤로 보낸 것은 초 단위로 주입됐다(`m-3f704032` 3초, `m-1fe57886` 2초).

관측 힌트: 누락 3건이 **17:35~17:36 1분 안에 몰려** 있고, 그 시간대에 수신 세션들이 장시간 도구 실행(대용량 SQL·cargo) 중이었다. **웨이크 훅이 바쁜 세션에 못 붙는 경로**가 의심된다.

## C — 주입 지연 편차 2초 ~ 9분

```
m-b6a27da7 18:18:13 → injected 18:24:19   (6분 06초)
m-ff1ba5f9 18:25:45 → injected 18:34:57   (9분 12초)
정상군: 2~10초
```
조율 용도에서 이건 결함이다. "그 방향으로 가지 마라"가 상대가 이미 그 방향으로 구현을 끝낸 뒤 도착한다. 오늘 실제로 내 정정이 도착하기 전에 상대가 독립적으로 같은 결론에 도달해 있었다(결과가 같아서 사고는 안 났다).
→ 주입 지연을 `agents`/`inbox` 에 p50/p90 로 노출하거나, 임계 초과 시 발신자에게 즉시 알림.

## D — 실패를 정확히 1시간 뒤에 알려준다

만료 통지가 전부 **발송 + TTL(3600s)** 에 도착한다(17:20:31 → 18:20:31, 4건 동일 패턴). 조율에서 1시간은 영원이다.
→ 수신자가 live 인데 3~5분 내 주입되지 않으면 **즉시** 발신자에게 통지. TTL 만료는 최종 정리용으로만.

## 부수 — 권고 문구가 비용을 유발한다

통지가 "blocking 으로 다시 보내면 부활 응답 경로를 탄다"를 권하는데 **부활은 유료**다. A 처럼 이미 배달된 건에 이 권고가 붙으면 불필요한 비용을 유도한다. `inject_count > 0` 이면 이 문구를 빼야 한다.

## 영향 요약

PM 운영 1시간에 브리핑 3건 완전 누락 + 1건 오진 + 지연 최대 9분. 대응으로 지시·결정은 전부 GitHub 이슈에 영구 기록하고 am 은 보조 채널로 강등했다. 위 메시지 ID 로 서버 로그를 대조하면 재현 근거가 될 것이다.
